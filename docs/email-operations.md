# Oyinca transactional email operations

## Implementation truth

Oyinca email/password authentication is owned by `apps/api/src/auth`; it is not Supabase Auth. Users, verification tokens, password-reset tokens, and session cookies are managed by NestJS, Prisma/Postgres, and the shared JWT cookie flow. Supabase is currently used for database hosting and realtime features only.

Email/password signup is a two-stage activation flow. Registration stores only a short-lived `PendingRegistration` containing the normalized email, bcrypt password hash, name, hashed verification token, and expiry. It has no tenant or product access. Clicking the verification link atomically creates the verified `User`, organization, membership, primary brand, and free subscription, then deletes the pending record. A failed or ignored verification email therefore never creates an account.

Transactional email is sent server-side by `EmailService` through SMTP. Browser code never receives SMTP credentials. Production requires all of:

- `SMTP_HOST`
- `SMTP_PORT`
- `SMTP_USER`
- `SMTP_PASS`
- `SMTP_SECURE`
- `EMAIL_FROM`

`EMAIL_FROM` should be `Oyinca <no-reply@auth.oyinca.com>` after that domain is verified. `APP_URL` must remain `https://oyinca.com` so verification and reset links use the canonical production origin.

## Incident recorded 2026-09-20

A fresh production signup created the user successfully, then Gmail SMTP rejected authentication with SMTP response `535 5.7.8 BadCredentials`. The old adapter returned `false`; registration ignored that result and returned HTTP 201 with a false “sent” message. No public MX, SPF, DKIM, or DMARC records were present for `oyinca.com`, and there was no explicit `EMAIL_FROM` production variable.

The application now treats provider acceptance as part of signup success, redacts recipients in logs, supplies plain-text fallbacks, and establishes the authenticated session when verification succeeds. SMTP acceptance is still not proof of inbox delivery; provider delivery logs remain the delivery authority.

## Resend activation runbook

Use `auth.oyinca.com` for authentication mail and keep future marketing mail on a separate subdomain. Do not invent DNS values.

1. In the owner’s Resend team, add `auth.oyinca.com` as a sending domain.
2. Copy the exact SPF and DKIM records generated by Resend into the current authoritative DNS provider (Vercel DNS at the time of this audit).
3. Add a conservative DMARC record only after reviewing every legitimate sender for the hostname. Start with monitoring rather than `p=reject`.
4. Wait for Resend to report the sending domain as verified.
5. Create a restricted production API key and configure Vercel Production and Preview separately:
   - `SMTP_HOST=smtp.resend.com`
   - `SMTP_PORT=465`
   - `SMTP_SECURE=true`
   - `SMTP_USER=resend`
   - `SMTP_PASS=<Resend API key>`
   - `EMAIL_FROM=Oyinca <no-reply@auth.oyinca.com>`
6. Redeploy, submit a fresh signup, and confirm both SMTP acceptance in Oyinca logs and `delivered` in Resend’s delivery log.
7. Configure a verified Resend webhook for `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, and `email.failed` before treating application-side acceptance as end-to-end delivery observability.

Resend documents `smtp.resend.com`, username `resend`, API-key password, and SMTPS port 465 as its recommended SMTP configuration. DNS records must still come from the specific Resend domain screen.

## Business addresses

The domain currently uses Vercel DNS, not Cloudflare DNS, and has no MX records. Cloudflare Email Routing cannot be enabled safely without first moving authoritative DNS or deliberately choosing another inbound provider. Do not change nameservers or MX records as part of the transactional-email repair.

The desired aliases remain:

- `hello@oyinca.com`
- `support@oyinca.com`
- `founders@oyinca.com`
- `privacy@oyinca.com`
- `security@oyinca.com`
- `billing@oyinca.com`

Creating them requires an owner-selected destination mailbox. Forwarding receives mail only; replying from the destination mailbox may expose that mailbox address unless a separate outbound mailbox or authenticated “send as” identity is configured.

## Verification checklist

For every production test, record separately:

1. API account creation response.
2. SMTP provider acceptance.
3. Provider event: delivered, bounced, complained, blocked, or failed.
4. Link resolves to `https://oyinca.com/verify-email`.
5. Verification creates the httpOnly session cookie.
6. A new user enters dashboard onboarding; an onboarded user enters the dashboard.
7. Reused and expired tokens fail without creating a session.

Never log passwords, raw verification/reset tokens, API keys, SMTP credentials, access tokens, refresh tokens, or full recipient addresses.
